# 队友更新了代码，我要怎么用？

> 这篇是回答一个具体问题：**"队友在仓库里更新了代码，我要怎么用上？"**
> 结论先放最前面：**一条命令**。
>
> ```powershell
> cd C:\Users\25643\Desktop\ai自动建模插件
> python tools\git_sync.py pull
> ```
>
> 它会把队友的更新拉下来、落到你平时用的工作目录、顺手跑自检告诉你"能不能用"。
> 下面解释为什么需要这么一条命令、它到底做了什么、出问题怎么退回去。

---

## 1. 为什么不能只 `git pull` 就完事

关键事实（都实测过，不是推测）：

| 事实 | 数字 / 说明 |
|---|---|
| GitHub 私有仓库里**只有代码** | https://github.com/Mary111222/AI-_- ，602 个文件，27 MB 量级 |
| 大数据**故意不进仓库** | `kb/real_brep` 116 MB、`kb/real_brep_coarse` 115 MB、`_wheels` 513 MB、现场照片、`零件参数`（客户资料） |
| 大数据在**你的工作目录**里 | `C:\Users\25643\Desktop\ai自动建模插件` |
| 但工作目录**不是 git 仓库** | 它没有 `.git`，所以在那儿 `git pull` 是不成立的 |

于是"用队友的更新"必然是两步：**先在仓库工作副本里拉取 → 再把改动落到工作目录**。
`tools\git_sync.py` 把这两步（外加验证与回滚）包成了一条命令。

## 3. 它到底做了什么（四步，每步都可核对）

| 步骤 | 做什么 | 安全性 |
|---|---|---|
| ① 取最新 | 用 GitHub Desktop 已登录的令牌 `git fetch`（令牌只在内存里，不落盘、不进命令行、不打印） | 只读，不改任何东西 |
| ② 快进合并 | 在协作包里 `git merge --ff-only origin/main` —— **不许自动产生合并提交** | 如果有本地未提交改动会直接失败并告诉你，不会硬覆盖 |
| ③ 镜像文件 | 按 `git diff 旧..新` 的清单，把**队友真正改过的文件**拷到工作目录 | 只碰这些文件；覆盖前先备份到 `_mirror_backup\<时间戳>\`；内容其实一样就不动 |
| ④ 跑门禁 | 在**工作目录**里跑 `python -m ai_modeler --selftest` | 不过就明确告诉你"先别用" |

### 镜像时特别注意的两件事

1. **保持你原来的目录布局**。仓库里文档是归档进 `docs/历史报告/`、启动脚本进 `启动脚本/`，
   而你工作目录里这些文件在根目录。脚本会识别这种"重新归档"，**仍然写回根目录**，
   不会在你工作区里凭空多出一堆目录。
2. **队友删掉的文件**：只有确认你本地那份**没被改过**（拿 git 的哈希比对）才会删；
   你改过的话会明确打印 `[保留(你本地改过)]` 而不动它。

## 5. 门禁没过怎么办：退回更新前

```powershell
python tools\git_sync.py rollback
```

它会：

* 把协作包 `git reset --hard` 回**上一次 pull 之前**那个提交（脚本自己记了）；
* 把这次被覆盖/删除的文件从 `_mirror_backup\<时间戳>\` 还原回工作目录。

**一个诚实的限制**：队友**新增**的文件不会被自动删掉（脚本不猜你想删什么），
要清就手工删，或者 `git clean` 那类操作 —— 我选择"宁可留一个多余文件，也不误删你的东西"。

## 7. 常见问题

**Q：pull 时提示 `快进合并失败`？**
A：多半是协作包里有未提交的改动（比如你自己在包里改过文件）。脚本不会硬来，会告诉你去看 `git status`。
   想干净重来：`cd` 到协作包 → `git status` 看清 → `git stash` 或提交后重试。

**Q：会不会把我在工作目录里的改动冲掉？**
A：只对"队友这次改过的文件"动手，覆盖前还会备份。但**同一个文件你俩都改了**的情况无法自动判断
   （工作目录不是 git 仓库，没有"本地改动"这个概念）—— 所以：**如果你正在改某个文件，先别 pull**，
   或者用 `python tools\git_sync.py check` 先看看清单里有没有它。

**Q：队友不小心把大数据推上去了怎么办？**
A：`.gitignore` + `tools\check_share_pack.py` 会挡住（四项判据里就包含误伤检查）。
   如果已经推上去：GitHub 单文件超 100 MB 会直接被拒；
   已经进去的要用 `git rm --cached` 停跟踪，历史里的大文件只能靠重建仓库或 `git filter-repo` 清。

**Q：我自己的改动怎么给队友？**
A：两条路：
   1. **直接改协作包里的文件**（那个目录就是 git 工作副本），然后
      `python tools\push_to_github.py status` → `push`；
   2. 改工作目录后，把改动同步进包再推（这一步目前要手工拷，因为工作区不是 git 仓库）——
      想常态化的话建议哪天把工作目录也变成 git 工作副本，我可以帮你做，但要先搬几个目录的位置。
