## 资源与依赖

- Rust 原生接管桌面模型 UI 中此前走 `backend_call` 的模型操作、旧集成菜单和通用 Python backend 启动器。
- 安装资源 builder 使用明确的文件清单：包含 CATIA COM adapter、`pywin32==312` bootstrap 资源、Agent 插件/提示词、所需知识库/训练语料、文档、固定 DSH manifest 与 OCCT runtime；不再打包整个 `ai_modeler` Python backend 或通用桌面 Python requirements/bootstrap。
- CATIA CPython/pywin32 安装到应用私有 `runtime/catia-python`，只由 CATIA adapter 路径按需准备；不回退到全局 PATH Python。开发 checkout 只查找项目 `.venv`。
- DSH 继续使用固定 Node/DSH runtime；Agent 所需的私有 Node 与 Python CATIA runtime 是不同资源。
- OCCT runtime 使用版本 manifest 与文件 SHA-256 校验；本构建复用 F4 runtime manifest，资源内容只复制到当前 worktree 的忽略构建目录。

## 2026-10-04：clean-target package 的 OCCT transitive dependency 修复

- 集成 HEAD `1fdd64636f54b42d160d4c7015719d0e3c06b545` clean-target build 的 package staging 曾有 17 个 DLL，遗漏直接依赖 `TKOffset.dll`；添加 TKOffset 并重建后 staging 为 18 个 DLL（含 TKOffset），System32-only headless Quick smoke 仍报告 `无法加载 OCCT bridge：LoadLibraryExW failed`。
- 使用 MSVC `dumpbin /DEPENDENTS` 静态检查 bridge 与所有已打包 OCCT DLL 的 PE import graph，唯一不在 stage/System32 的解析项为 `TKOffset.dll → TKFillet.dll`。源 runtime bin 中有 `TKFillet.dll`，package stage 和 System32 均没有；TKFillet 的 PE imports 均由 staged OCCT/MSVC DLL 或 Windows 系统/API-set imports 满足。bridge 使用绝对 DLL 路径和 `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`，因此把 PATH 扩回开发环境不会修复受限 PATH 场景下的缺包问题。
- 作为诊断实验，集成侧临时把源 runtime bin 的 `TKFillet.dll` 复制到 ignored package staging 后，在 PATH 仅含 System32 的条件下 Quick smoke 返回 `status=ok`，geometry 为 1 个闭合实体、100×60×20 mm，Python/Node child 均未启动。这验证了加载失败由 staged runtime 缺少该传递依赖引起；由于 DLL 是手动补入 staging，该次结果不是正式 staging/package 验收。
- 本修复将 `TKFillet.dll` 加入 Build-Runtime、manifest writer、Rust validator 与 JS package allowlist；runtime 闭包为 15 个 OCCT DLL（CMake bridge 的 14 个直接链接 toolkit 加 `TKFillet`）、bridge 1 个和 MSVC runtime 3 个，共 19 个 DLL。漂移回归要求 CMake 直接链接列表是 runtime 列表子集、Build-Runtime/manifest/Rust/JS runtime lists 完全一致，并显式锁定 `TKOffset.dll → TKFillet.dll`。
- Build-Runtime、manifest writer、Rust allowlist、JS package allowlist 与 fixtures 已加 TKFillet。最终修复后的 staging、安装包编译与正式 System32-only headless smoke 结果见下方“最终打包复验”；此前 17-DLL/18-DLL stage 及手工补 DLL 的诊断实验仍不能代表正式验收。
