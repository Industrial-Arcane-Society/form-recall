# F6.8：将完整 DSH Runtime 依赖打入桌面安装包

日期：2026-10-05

后续更新：本文记录 F6.8 的 DSH Runtime 离线包。F6.9 又将 WebView2 x64 离线安装器纳入 MSI/NSIS，因此本文下方 218.30/204.45 MiB 是 F6.8 单独完成时的包体，不是当前完整离线安装包大小；当前数据以 [F6.9 WebView2 离线运行时记录](./94-f6.9-offline-webview2-runtime.md) 为准。

## 目标

桌面安装包不再只是携带 DSH 的 manifest、`package.json` 和 lockfile；必须同时包含固定版本的 Node.js、npm、DSH/ACP、SDK 及 lockfile 安装出的 Windows x64 依赖。用户首次使用 Agent 时只把离线包解压到当前用户数据目录并校验，不应下载 Node 或在用户机器执行 `npm ci`。

Quick/本地建模不依赖这份 Agent Runtime。开发模式没有离线包时仍保留既有网络安装回退，便于 `npm run dev`。

## 实现

- `build_desktop_resources.mjs` 根据 `runtime-manifest.json` 和 `package-lock.json` 构建 Node `v22.23.3`、npm `10.9.9`、DSH/ACP `0.2.0-rc.2` 与 ACP SDK `1.4.0` 的 Win x64 运行树。
- 打包前校验 Node、npm、DSH CLI、ACP 与 SDK 版本及 package/lockfile SHA；构建出的运行树压成一个 ZIP，避免把近三万个散文件逐项交给 MSI/NSIS。
- `runtime-bundle-manifest.json` 将 ZIP SHA、压缩/解压大小、文件数、平台、依赖版本和源 lockfile SHA 绑定。构建缓存只有在版本与 hash 同时匹配时才复用。
- Rust Release 路径要求随包 ZIP；首次安装在临时 staging 目录内检查哈希，拒绝越界/重复/符号链接，按清单校验解压文件数和字节数，再核验 Node/npm/DSH/ACP 版本并原子启用。解包期间按字节进度回报 UI。安装命令使用 16 MiB 专用线程栈，对齐先前冷安装实测可用的线程配置；启用遇到 Windows 文件占用时短暂重试；失败时删除 staging、保留当前已安装版本。安装完成后，用户会话、profile 和 `DSH_HOME` 仍保存在用户目录。
- Debug 开发路径在没有 ZIP 时继续使用原有 Node 下载与 npm lockfile 安装逻辑；UI 根据 Runtime 状态说明正在本地解包还是开发环境安装。

## 验收结果

- 构建脚本从此前已由生产安装函数安装并校验的本机 Runtime 树制包；节点和来源清单匹配当前固定版本。生成 ZIP 为 198,590,382 字节，SHA-256：`6a388f3757a4f75d8a92d901598b2ff9df03abd8ee76a30731fea99be224f57d`；内含 28,612 个文件，解压大小 583,769,994 字节（556.7 MiB，按 ZIP 中所有文件条目长度求和，按 1 MiB=1,048,576 bytes 四舍五入）。
- 用生产 `dsh_runtime::install()` 在新的隔离用户数据目录中，从**最终 MSI 管理抽取目录**读取 ZIP 并本地解压成功；状态返回 `bundled=true`、`installed=true`，进度回报 15% 至 98%，`node --version` 返回 `v22.23.3`，`dsh --version` 返回 `0.2.0-rc.2`，重复安装正确复用现有版本。该路径未运行 npm 安装或下载 Node。
- F6.8 单独交付阶段的 MSI 和 NSIS 包都已构建；最终 MSI 管理抽取、NSIS 7-Zip 抽取后的 ZIP 均为 198,590,382 字节，SHA 与 staging 完全一致；两个包都具备核心静态资源 13/13、`runtime-bundle-manifest.json` 和 lockfile。当时的产物大小为 MSI 218.30 MiB、NSIS 204.45 MiB。F6.9 后续把 WebView2 离线安装器并入两种包，当前较大的最终包体和 SHA 见 F6.9 文档。
- 静态资源专项复核：MSI/NSIS 抽取结果均存在 `app/kb/native_knowledge_enrichments.v1.json`（5,321,723 bytes；SHA-256 `f7ac3ea1377f2213af456ef1716a395b5dd4349bbfc675393b7750862f25a561`）及 `app/ai_modeler/catia_com_adapter.py`（23,580 bytes；SHA-256 `121c07c325e88bc8a8d0b2629ca68d11fab588df4eb2a9a5ec22b7f247fc89a6`），与源码和 staging 一致。完整资源目录逐文件对拍为 `missing=0, extra=0, mismatched=0`；MSI、NSIS 各有 148 个 app 文件，连同 Python、CATIA bootstrap 和 OCCT Runtime 共 207 个资源文件。实际检查了 ZIP entries、依赖入口和版本，不只是依赖清单。
- 安装页缺少资源截图的复核边界：截图错误涉及静态知识/adapter 文件，与完整 Node/DSH 依赖 ZIP 是两类资源；当前包内静态文件齐全。没有运行安装后的 Tauri GUI，因此截图所用程序版本和实际 `resource_root` 仍未知；不能把“旧程序或运行时路径不一致”写成已证实根因。
- 曾有一次较深隔离路径在完成解压后原子切换报 Win32 `ERROR_ACCESS_DENIED`；原因未能确认。加入短暂重试和切换失败时 staging 清理后，在较短的新隔离数据目录复测通过。不要将该次失败误记成首次 MSI 内容缺失。
- 前端 production build 通过。生成的 Tauri Release binary 已完成构建。

### 2026-10-05：包内 Runtime 冷启动复核

- 使用生产 `dsh_runtime_cli_smoke.exe`，以当前 staging 的 `target/package-resources/app` 为安装资源根，在全新隔离用户数据目录执行冷安装；将 `PATH` 限制为 `%SystemRoot%\System32`，并清除 `PYTHON*`、`NODE*`、`NPM*`、`DSH*` 环境变量。CLI 退出码为 0：初始状态为 `bundled=true, installed=false, bundleRequired=true`，从随包 ZIP 本地解压后报告校验成功，`node --version` 为 `v22.23.3`，`dsh --version` 为 `0.2.0-rc.2`，重复安装为幂等成功。
- 隔离安装目录的 `install-manifest.json` 记录 `runtimeSource=bundled`，ZIP SHA-256 为 `6a388f3757a4f75d8a92d901598b2ff9df03abd8ee76a30731fea99be224f57d`。从新安装目录直接运行 Node 与 DSH CLI 也都退出 0、版本吻合。没有通过 npm 安装，也没有联网下载运行依赖。
- **证据边界：**本次实际执行的是包内 staging 资源，不是安装后的 MSI/NSIS `resource_root`。复用的 CLI harness 构建时间早于 `dsh_runtime.rs` 提交 `94d4ca2` 约 19 分钟；虽然该 Rust 模块自该提交以来没有后续变更，现有证据不能证明 harness 与当前提交逐字节同源。尝试从当前源码重建 standalone harness 时遇到 Win32 `os error 299`，复用 Cargo target 的 debug/release 链接分别因 MSVC CRT/WebView2 未解析符号失败。因此记录为生产 CLI 包内 Runtime 冷启动通过，harness 当前源码重建与实际安装器冷启动仍待验。
- **2026-10-05 fresh-worktree build check：**在 `ad8b68238c896a24aa1b6e46a45e01a13ea68739` 的干净源码 worktree，直接执行 `cargo build --manifest-path src/apps/desktop/src-tauri/Cargo.toml --bin ai-modeler-headless-smoke` 时，Tauri build script 因未生成的 `target\package-resources\app` 资源路径而失败。只在该 Cargo 子进程设置 `TAURI_CONFIG={"bundle":{"resources":[]}}` 后，headless smoke binary 从当前 crate 源码成功构建（dev profile，约 68 秒），没有改动配置文件。该 binary 是 F4 native Quick smoke，不包含 DSH runtime CLI；因此这次结果只证明当前 crate 的 smoke 构建可在无发布资源 staging 时完成，**不**解决早先生产 DSH harness 与当前源码的同源性缺口，也没有重新执行 DSH ZIP 解包。旧 harness 原先记录的 linker 报错在该新构建路径中没有复现；Win32 `os error 299` 和旧 target 的 CRT/WebView2 符号问题仍是历史诊断，未在此复现或确认根因。

### 2026-10-05：从 main `96d15ab` 源码构建的 Release 冷启动 CLI

- 在独立分支 `feat/f6-8-dsh-cli-acceptance` 的提交 `cf95b04` 新增 `dsh-runtime-coldstart` headless bin。它直接调用生产 `dsh_runtime::status()`、`install()`、`resolve()`，使用本地 `tauri::ipc::Channel` 接收进度，不启动 Tauri Runtime/GUI，也不调用 Agent、provider 或 CATIA。
- 使用 main checkout 的 `src/apps/desktop/src-tauri/target/package-resources/app` 作为只读安装资源根。该 staging ZIP 为 198,590,382 bytes，bundle manifest SHA-256 `6a388f3757a4f75d8a92d901598b2ff9df03abd8ee76a30731fea99be224f57d`；生产 `status()` 与 `install()` 校验 ZIP hash、大小、文件数以及 source manifest/package/lock 对应关系。staging 的 `runtime-manifest.json`、`package.json` 和 `package-lock.json` 与 main 当前源码逐文件 SHA-256 一致。
- Release binary 从本分支源码在独立 worktree 的空 Cargo target 中以 `cargo build --offline --manifest-path src/apps/desktop/src-tauri/Cargo.toml --release --bin dsh-runtime-coldstart` 构建；只为这次 Cargo build 设置 `TAURI_CONFIG={"bundle":{"resources":[]}}`，避免新 worktree 缺少发布资源 staging 时 Tauri build script 提前失败。运行时没有重用早先的 `dsh_runtime_cli_smoke.exe`。
- 运行时将 CLI 进程 PATH 限制为 `%SystemRoot%\System32`，按变量名清除 Python/Node/NPM/DSH 与常见 API key/token/secret/password/credential 环境变量；没有读取或输出这些变量的值。CLI 退出码为 0：首次状态 `bundled=true, installed=false`；首次 install/resolve 成功后为 `bundled=true, installed=true`，manifest 记录 `runtimeSource=bundled` 与相同 bundle SHA；Node `v22.23.3`、npm `10.9.9`、DSH `0.2.0-rc.2` 的实际私有 CLI 输出均匹配清单。重复 install 后 `installedAt` 未变化，幂等检查通过；安装过程共捕获 13 个 progress event。
- 这是当前源码 CLI 对 `target/package-resources/app` staging 的离线冷启动证据。没有安装 MSI/NSIS，也没有验证安装器解包后的 `resource_root` 或新账户 GUI 首启；后两项仍需独立验收。此前早约 19 分钟构建的 `dsh_runtime_cli_smoke.exe` 保留为旧 harness 历史证据，不再作为当前源码验收依据。

## 验收边界

- 未启动可见 GUI，也未安装 MSI/NSIS 到主机；运行时验收使用生产 Rust 模块与 CLI harness，没有经过 Tauri 窗口。
- 未启动 DSH ACP 对话或向模型 provider 发请求；本项验证的是 Runtime 文件齐全、可从随包依赖解压并运行 CLI。Agent 会话、多模态和 CATIA 验收属于独立链路。

## 可复现构建

```powershell
cd src/apps/desktop
npm ci
npm.cmd run tauri:build
```

首次构建机需要从固定源获取构建时 Node/lockfile 内容及既有 CATIA wheel；之后 DSH ZIP 会在 `src/apps/desktop/src-tauri/target/package-downloads/` 留有按 manifest 和 SHA 校验的构建缓存。最终用户运行 MSI/NSIS 时不需要网络安装 DSH npm 依赖。
