### 为什么主解析"暂缓切换"

新参数表在**逐键对拍**里已能对上大部分取值，并在若干处**比旧解析更对**
（例：盘形凸轮的"基圆直径"、符号式"n3"），但整体切过去后带轮题库**一度从 100% 掉到 41%**。
根因是"规则顺序 + 数字边界"联动很敏感：

| 踩过的坑 | 现象 | 修正 |
|---|---|---|
| 计数规则排在别名之前 | 「槽数5」的 5 先被占走 → 「孔径45」被挖成"孔径4" | 规则顺序改为**别名优先** |
| 短别名抢先 | 「槽数3」被别名"槽"抢走 → 槽数读成 30/40 | 加**别名后缀消歧**（数/型/宽/距/深…） |
| 数字后边界过严 | 连写「槽数3A型」被误杀 → 槽数变 0 | 连写改由 `add_boundaries()` **提前补边界** |
| 占用遮罩参与前后判定 | 「内径22 宽度12」里宽度被换成典型值 | 前后判定必须看**原文** |

四处都已修，但两条路径并存时状态仍多，仍有零件在切换后取到典型值。
按本文档 §7 定的"**任一掉绿即回退**"，本轮把开关默认关，把迁移作为下一步独立工作项
（逐个零件切换 + 每次跑满四套回归）。

> 地基（ParamTable / extract / 对拍工具）已在仓库里可直接启用；缺的是逐零件迁移与验证的工作量。

开关打开时出现"参数表取值正确、下游几何被改错"的现象：
`model_params` 返回 `d=20 D=47 B=14`，但 `nlparser` 出来的特征变成
`cylinder radius=2.0`、`gear teeth=2`。**提取层没问题，问题在同一条链路上**
（`_clamp_cuts` 的外径判定被多余键污染 / 特征名映射）。已修掉其中一处
（不再把内部量 `pitch_d` 塞进 params），但下游仍有干扰，因此按规则回退。

**本轮实修的两个真 bug（都已生效、四套回归全绿）：**

1. **`in` 对字符串是子串匹配**（`params.py`）：
   `_tail in _ALIAS_SUFFIX_BLOCK` 里 `'60'` 被判为命中，导致「长度60 / 长度40 / 厚度3」
   **整类读不到**（长度全部丢失、厚度被读成 2）。改为成员集合判断后恢复。
   教训：凡是"检查单个字符是否属于某集合"，必须用 `set` 或逐字符比较。
2. **标准直径系列表列映射错位**（`tools/extract_pulley_std.py`）：
   同一槽型在表里出现多次（左半区/右半区/大直径续列），早先只取**第一个**出现的列，
   于是 A 型的值取到了 B 段 —— 实测 **A 型 ⌀100 抽成 104**（那是 Z 型的值）、
   B 型抽成 105.5。加入"**合并列对一致性校验**"（同一槽型的相邻两列必须重复同一数值，
   不一致则整行丢弃）后修正为 **A ⌀100 = 105.5**（与标准知识一致）。
   教训：这类"数值看起来合理、其实是别的槽型的数"的错误最难发现，
   必须靠**冗余校验**（两列应相等）而不是靠肉眼看。

### 0.3 第 4 轮：修掉两个真实几何缺陷 + U3 公差闭环交付

**① 同步带轮齿形做成了轴向槽（上一轮 V2 抓出来的）—— 已修**

`make_timing_pulley()` 把齿形当**轴向剖面**去回转，而齿是**角向**特征：
那段剖面沿轴向就跨了 z·p（20 齿 × 5.08 ≈ 101mm），回转 360° 时自身缠绕。
改成：盘体回转 + **每个齿一个 2D 多边形沿 Z 拉伸** + 绕轴均布。
实测：轴向 99.09 → **30.00**（期望 30），外径 81.143（精确）。

**② V 带轮轮缘宽度被撑大 6.6mm —— 已修，根因值得记下来**

| | 数值 |
|---|---|
| 现象 | 3 槽 A 型轮缘宽度几何 46.32，而标准值 39.32 |
| 根因 | 留边 `f` 只按**槽口半宽**算，但 **V 槽根部比槽口更宽**（张开），槽底因此戳出端面 |
| 修正 | `f = max(槽口半宽, 槽底半宽)`；轮廓里的夹紧也按槽底最宽处 |
| 结果 | 几何 46.32 = 期望 46.32（口径一致），5 项受控尺寸**全部通过** |

> 这条只有"从几何反量尺寸"才可能发现 —— 以前只看包围盒差 2%，它会躲在公差带里。

### 0.5 第 6 轮：U5 链轮标准数据交付（28 链号 / 锚点自检 8-8）

**① 新增 `tools/extract_sprocket_std.py` + `ai_modeler/std_sprocket.py`**

数据源：机械设计手册「滚子链的基本参数与尺寸(**GB/T 1243—2006**)」
（`https://www.jlc-jdgf.com/mcbook/GBT1243-1.htm`，75 行网格）。
抽出**28 个链号**的节距 p / 滚子直径 d1 / 内链节内宽 b1 / 销轴直径 d2 / 内链板高度 h2。

**抽取过程中踩的坑（值得记）**：这张表是**上下两段** ——
第一段是"链条主要尺寸"，第二段是"链条全宽 b4/b5/b6"。同一链号在两段都出现，
不加区分会把第二段的数字当成节距（实测 08A 的 p 被读成 11.18、d1 读成 11.23）。
- 我先后试了两种判据：① "两段数值必须一致"（太严，结果 0 条）；
  ② **物理合理性**：滚子直径与节距有稳定关系 `d1 ≈ 0.5~0.7·p`，用它挑出正确的那一段 —— 成功。
- 自检锚点（公开标准值）：08A p=12.7/d1=7.92、**12A p=19.05/d1=11.91**、16A、20A、24A、06B、08B
  **全部 8/8 通过**。

**② `std_sprocket` 提供标准公式**（查不到链号就**明确报错**，绝不静默取近似）：

| 量 | 公式 |
|---|---|
| 分度圆直径 d | `p / sin(180°/z)` |
| 齿根圆直径 df | `d − d1` |
| 齿顶圆直径 da | `p·(0.54 + cot(180°/z))` |
| 齿沟圆弧半径 ra | `0.5025·d1 + 0.05` |
| 齿宽（单排） | `0.93·b1` |

实测（08A、19 齿）：分度圆 ⌀77.16、齿根圆 ⌀69.24、齿顶圆 ⌀82.96；
（12A、25 齿）：分度圆 ⌀151.99。链号写法归一支持 `8a`/`08a`/`12A-1`。

#### 9.3 纠正我自己的一个**误判**（记录下来以免重蹈）

过程中我一度断定"10 齿的齿比齿距还宽、齿互相重叠、几何是坏的"。**这个判断错了。**
把齿顶顶点（r ≥ 0.99·r_max）列出来就清楚：

```
成对出现：6.93/29.07 是同一齿的两条棱边（隔 22.14°），
         下一齿再隔 22.14° —— 周期 36° = 360/10 ✅
```

齿顶是一条**平面**，有两条棱边，所以"每齿 2 个凸起 / 2 个凸顶顶点"是**正常形状**。

#### 9.4 本轮真正落地的几何改进：齿距自洽性检查

排查中发现一个**该报没报**的情形：齿的切向宽度是**常数**（= 标准齿顶宽），
而切向齿距随直径变化；当齿顶处切向齿距小于齿顶宽时相邻齿必然重叠、齿形不可用。

判据（⚠️ 取**齿顶圆**处的切向齿距，不能拿节圆处齿距去比齿顶宽，那样偏松）：

```
切向齿距(齿顶) = 2π·r_tip / z        r_tip = dd/2 + 0.45·tooth_h
若 2π·r_tip/z < tooth_tip  ->  报警，并给出两种改法
```

已并入 `partlib._timing_pulley` 的 `std_warnings`，报警文案同时给出
"要达到该齿数所需的最小节圆直径"与"该直径下可用的齿数"，用户不必自己反算。

#### 9.1 缺陷一：`cn_count` 把跨参数的数读成一段（齿数读错的根因）

症状（上一轮记录）：

```
同步带轮 节圆直径20 20齿 XL型   -> teeth=12（应为 20）
同步带轮 节圆直径80 40齿 XL型   -> teeth=49（应为 40）
```

**根因不是"粘连拆分"逻辑本身，而是占用判定的坐标算术。** 实测打印：

```
work  = '同步带轮 节圆直径20 20 齿 XL型'
blank = '同步带轮        20 齿 XL型'      ← 别名规则已把"节圆直径20"挖成遮罩
spans(orig) = [(5, 11)]                  ← 节圆直径占用的原文区间
i=15 k=12 k_sep=4                        ← k_sep 向左穿过了**整段遮罩**
to_orig_span(k_sep, i) = (4, 15)         ← 区间被撑宽到 4..15
is_free(4,15) = False                    ← 明明空闲的 20 被判成已占用！
_free_w(k=12, i=15) = True               ← 只用数字本身则判定正确
```

两处错在一起：

1. `k_sep` 为了"把分隔空白算进来"一路向左吸，**把占位符 `\u0001` 也当成了空白**，
   于是穿过整段遮罩落到 4；
2. 占位符是**等长**的，一段遮罩的起止映射回原文会得到**比原占用区间更宽**的区间，
   所以用"换算后求交"判断占用必然误判。

**修法**：占用判定改成**直接看遮罩**——区间里有没有 `\u0001` 就是有没有被占用。
既不依赖坐标算术，也不会被遮罩宽度影响：

```python
def _free_w(self, i, j):
    blank = self.tab.blanked_text()
    a, b = max(0, int(i)), min(len(blank), max(a + 1, int(j)))
    return "\u0001" not in blank[a:b]
```

`cn_count` 的区间同时改回 `[k, i)`（数字本身，不再向左吸空格/遮罩）。

**验证**（5/5）：

| 输入 | 修前 | 修后 |
|---|---|---|
| 节圆直径20 20齿 XL型 | teeth=12 ❌ | **teeth=20 ✅** |
| 节圆直径80 40齿 XL型 | teeth=49 ❌ | **teeth=40 ✅** |
| 节圆直径50 齿数20 T5型 | — | teeth=20 / T5 ✅ |
| 宽度40 4个槽（原本就正常的粘连写法） | 4 ✅ | **4 ✅（未破坏）** |

> 关键点：本项目**原本设计**的粘连写法（`宽度40` + `4个槽` → 取末位 4）**必须保住**。
> 上一轮我草率改动时正是打破了它才引入 `80 40齿 → 49`。这次先把
> "为什么之前会错"打印成事实再动手，一次改对。

#### 9.2 缺陷二：同步带轮被套上 V 带轮的槽型

症状：`同步带轮 节圆直径50 内径12 齿数10 宽10` → 齿型读成 `Y`。

### 0.15 第 10 轮：U1 主体 —— 通用形状的取值也带出处（0% -> 87.7%）

上一轮把"出处"从参数表贯通到了零件库特征，但通用形状
（长方体/圆柱/孔/弹簧/手轮…）走的仍是**另一条取值路径**：`nlparser.extract_dims()`。
本轮把它也接上。

#### 16.1 为什么没有直接重写 `extract_dims`

`extract_dims()` 是一个大正则解析器，同时被 **45 处**调用（孔位、阵列、圆角、
裸尺寸兜底、`partlib` 的旧解析…）。一次性把它改写成参数表驱动，
失败的表现是**几何静默错位**（不是崩溃），风险与收益完全不成比例。

改用的办法是：**值的来源仍然只有一处（原正则），出处就在同一段代码里顺手记下**。

* 新增 `DimTable`：字段名 -> `params.Value`（带 span / provenance）；
* `Dims` 增挂 `d.table`，并提供 `provenance_of()` / `span_of()` / `provenance_map()`；
* `extract_dims()` 里的**每一处赋值**紧跟一句 `T.note(...)`，记下区间与出处。

这样"值"和"出处"由**同一次正则匹配**同时产出，结构上不可能漂移；
并且完全不改变任何既有行为（下面有回归为证）。

#### 16.2 顺手抓到一个真的解析缺陷：中文乘号 `×` 不被识别

写三元组记出处时发现：`200×150×12` 的 `d.triple` 是 `None`，而 `100x60x20` 正常。
原因是最早的分隔符只写了 `[x*]`：

```
'200×150×12'   -> triple=None   raw=[200,150,12]   ← 中文乘号（U+00D7）
'100x60x20'    -> triple=(100,60,20)               ← ASCII x
'长方体 100*60*20' -> triple=(100,60,20)           ← 星号
```

`×` 恰恰是**中文图纸最常用的写法**。修好后：

```
'200×150×12'                     -> triple=(200,150,12)  prov: length/width/height
'底板 200×150×12, 四角各打一个直径8的通孔, 内缩12'
                                -> triple=(200,150,12) + diameter + count + margin
'100×60'                        -> pair=(100,60)
```

### 0.19 第 12 轮：U9 —— LLM 只出结构，不出数

升级文档的口径：LLM 只做 **① 意图理解 ② 结果解释**，**绝不做算术、绝不生成数值**。
理由很硬：通用 LLM 在参数精度上不可靠，数值幻觉会直接变成错误几何，
而且换模型/换温度结果就变，**不可复现**。

#### 19.1 先看清旧路径违反了哪一条

`ai_modeler/llm.py` 里的旧 `SYSTEM_PROMPT` 是这么写的：

```
- 单位一律换算为毫米。
{"kind": "box", "params": {"length":100,"width":60,"height":20, ...}}
```

也就是**要求模型把所有数字都算出来、还要做单位换算** —— 正是 U9 要禁止的那件事。

#### 19.2 新路径（`ai_modeler/llm_plan.py`）与一次真实的失败

新格式里每个数值必须是一个**引用**，模型一个数字都不许写：

```
{"kind": "cylinder", "op": "add",
 "params": {"radius": {"ref":"text","identifier":"直径"},
            "height": {"ref":"text","identifier":"高"}}}
```

**⚠️ 关于 identifier 与 span（这是实测踩出来的，值得写下来）**
第一版设计让模型给**字符区间** `{"ref":"text","span":[4,6]}`。实测立刻翻车：
对原文 `"圆柱 直径60 高120"`，模型给出 span [4,6]，那其实指向 `"6"`，
于是半径成了 **6.0** 而不是 30。

两处教训：
1. **LLM 数不准字符位置** —— 它不是在逐字符数，是在"猜大概在哪"；
2. **"直径60 → 半径30"本身就是算术**，正是不该让模型碰的东西。

所以改成：模型只说"这个值取自原文的**『直径』**"（参数名是稳定的短字符串，
模型在这件事上可靠），**取数与换算全部留在本地**（`nlparser.extract_dims` + 几何层）。
现在 `"圆柱 直径60 高120"` 求值得到 `radius=60`（**原始值，不做任何运算**），
`/2` 发生在下游本地几何层 —— 边界清楚。

#### 19.3 又抓到一个真 bug：校验函数写了却没被调用

`validate_plan()` 里定义了 `walk()` 用来检查引用**本身**是否合法
（未知 ref 类型 / text 缺 identifier / std 缺 key / ask 缺 question），
但**从来没有调用它** —— 等于这几条校验全是死代码。实测 4 类非法引用一个都没抓出来。

修法：每个参数值都交给 `walk` 过一遍（包括"看着不像引用"的那些，
否则 `{"ref":"telepathy"}` 这种写错类型的值会从两个分支的缝里漏过去）。

### 0.21 第 13 轮：U8 候选生成 + 可行性校验

升级文档口径：规格不全时给出 **2–3 个满足标准的候选**，用轻量代理指标排序，

新增 `ai_modeler/candidates.py`：

**① 候选只从本地标准表里取**，不生成数值。带轮候选要求"基准直径必须命中该槽型的

**② 不可行的组合直接淘汰**，不是排在最后：

### 0.22 第 13 轮：U6 约束求解（先诊断，再求解）

升级文档口径：引入 `ConstraintSolver`（自由度 x、约束 f(x)=0、Newton/LM + 冗余检测）；
风险与回退明确要求 **先做"检测与报告"（过约束/欠约束），再做求解**；提供手动摆位兜底。

新增 `ai_modeler/constraints.py`，两条实现纪律：

**① 先诊断，再求解。** `diagnose()` 用数值雅可比的**秩**判断：

| 情形 | 判据 | 行为 |
|---|---|---|
| `under` 欠约束 | 秩 < 自由度 | **拒绝给解**，说明还缺几条独立约束 |
| `over` 过约束 | 约束数 > 秩 | **拒绝给解**，列出冗余/冲突候选 |
| `well` 恰定解 | 秩 = 自由度 | 求解 |
| `empty` 无约束 | 没有约束 | 不当成错 |

冗余检测用"去掉某条后秩是否不变"—— 这正是"距离约束写了两遍"能被抓到的原因。

**② 只用标准库做数值线性代数**：高斯消元（部分主元）+ 中心差分雅可比 +
Levenberg–Marquardt 阻尼，不引入 numpy。规模是"草图级"（几个到几十个自由度）。

`force=True` 时才无视诊断强行迭代，且返回值**标明 `forced=True`** ——
避免"强行解"被误当成可信结果（对应文档里的"手动摆位兜底"）。

**③ 验收 `tools/check_constraints.py`：全部通过**

| 组 | 内容 | 结果 |
|---|---|---|
| A | 欠约束 -> 诊断 under、**拒绝给解**、原变量不被悄悄改动 | ✅ |
| B | 恰定解 -> 解到 (5,0)，残差 1.6e-11 | ✅ |
| C | 过约束 -> 诊断 over、列出冗余（含那条重复的距离约束）、拒绝给解 | ✅ |
| D | 无约束 -> `empty`，不算失败 | ✅ |
| E | `force=True` 才强行迭代，且标明 `forced`，诊断仍如实报告 under | ✅ |
| F | 解代回约束，最大残差 1.6e-11 | ✅ |
| G | 线性代数：奇异矩阵返回 None（**不硬凑一个解**）、相关两行秩=1 | ✅ |
| 附加 | 角度约束（解出 30.0000°）+ 长度 10 | ✅ |

## 四、P0 详细设计（可直接照着改代码）

### U1 两段式解析：先规划特征、再注入尺寸

**问题**：现在 `nlparser.handle()` 一边认词、一边解析尺寸、一边建特征，三者耦合；
任一环节误判都会污染后续（例如把"槽数3"读成切除要求）。

**改法**（对 Pointer-CAD v2 的 Plan-Then-Construct 做规则化实现）：

```
阶段 A：规划（只决定"建什么特征、什么顺序"，不碰任何数值）
    输入：规范化文本
    输出：DesignPlan = [
        {"id": "f1", "op": "ADD",  "type": "revolve_body", "role": "wheel_body"},
        {"id": "f2", "op": "CUT",  "type": "groove",       "role": "v_groove",
         "expr": "standard:GB10412:groove", "count": "@n", "pitch": "@e"},
        {"id": "f3", "op": "CUT",  "type": "hole",         "role": "center_bore",
         "dia": "@bore_d"},
    ]
阶段 B：参数注入（只填数值，来自"参数表"，不重新解析文本）
    输入：ParamTable（键 → 值 + 出处 + 置信度）
    输出：可构建的特征列表（Feature(...)）
阶段 C：构建 + 公差校验（见 U3）
```

**关键规则**
- 阶段 A **禁止**出现任何数字字面量：所有数值必须是 `@引用`。这样"数值读错"与"结构判错"被彻底分离，出错时能精确定位是哪一层。
- 阶段 B 只认 `ParamTable`。若某引用在表里缺失 → **不猜测**，走 U8 候选流程或直接在界面提问。
- 被"套典型值"的引用必须在 `ParamTable.provenance` 里标记 `default`，界面用不同颜色显示。

**伪代码**

```python
def parse_v2(text):
    doc_norm = normalize(text)
    table = extract_param_table(doc_norm)        # U2：只做"抽数值 + 记出处"
    plan = plan_features(doc_norm, table)        # 只做"抽结构"，不读数值
    for step in plan.steps:                      # 参数注入
        args = {}
        for k, ref in step.args.items():
            if isinstance(ref, Ref):
                if ref.key not in table.values:
                    return NeedInfo(step, ref)   # 缺参 → 提问，不猜
                args[k] = table.values[ref.key]
            else:
                args[k] = ref
        step.args = args
    feats = [build_feature(s) for s in plan.steps]
    report = verify_tolerance(feats, table)      # U3
    if not report.ok:
        return Reject(report)                    # 宁可报错，不交错的几何
    return Result(feats, report, table)
```

**验收**：500 题人工题库上，**参数层准确率 ≥95%**；且"静默错值"（构建成功但数值与提示词不符）**= 0**。

### U2 参数引用表 + 指针取值（禁止特征构建期再解析文本）

**问题**：数值散落在 `nlparser` 与 `partlib.model_params` 两处解析，重复且互相污染
（实测：「带轮 d25 D100 B30 n3 A型」里 `n3` 被 `B30` 干扰）。

**改法**：一次性抽出"参数表"，后续全部引用它。

```python
# ParamTable：键 → {value, unit, source, span, confidence, provenance}
#   provenance ∈ {explicit, standard, derived, default, asked}
#   span 记录该数值在原文本里的位置 —— 用于"这句话→这个数"的高亮与纠错
{
  "bore_d":  {"value": 25.0, "unit": "mm", "span": [8, 11], "provenance": "explicit"},
  "pitch_d": {"value": 100.0, "unit": "mm", "span": [11, 17], "provenance": "explicit"},
  "n":       {"value": 3,    "unit": "条", "span": [24, 27], "provenance": "explicit"},
  "gt":      {"value": "A",  "span": [28, 30], "provenance": "explicit"},
  "outer_d": {"value": 105.5, "source": "GB/T 10412 系列表", "provenance": "standard"},
  "width":   {"value": 39.32, "source": "标准轮缘最小宽度公式", "provenance": "derived"}
}
```

**取值规则（按优先级，命中即止）**
1. **纯符号区**：`d25 D100 n3` —— 要求独立成词，前后不得紧邻字母数字（修掉 `n3` 被 `B30` 干扰）。
2. **中文别名区**：`内径25`、`轮宽40` —— 命中后**把这段文本从工作串里挖掉**（占位符替换），后续参数看不到它（修掉「宽度303个槽」）。
3. **粘连拆分**：数字串后紧跟量词/关键词时按"最长合法前缀"切（`宽度40|2个槽`）。
4. **标准解析**：`A型` → 查标准表 → 补 `bd/ha/hf/e/φ`。
5. **推导**：`da = dd + 2·ha`、`rim_w = (n-1)e + 2f`。
6. **默认**：仅在"可选参数"上允许，且必须标记 `provenance="default"` 并显示给用户。

**验收**：把本轮 5 个历史 bug + 自动扩充的 66 题全部纳入回归集，**通过率 100%**，
且新增"任一参数不得在构建期被重新解析"的代码检查（grep 断言：`params.get(` 不允许出现字符串解析调用）。

### U3 公差级自检闭环（顶点 / 边 / 面三级）

**问题**：现在只有"包围盒差 2%"。构建成功但某个槽深差了 0.3 mm，程序完全无感。

**改法**（照搬 Pointer-CAD v2 的三级评测协议 + MBD 的基准/公差/测量点思想）：

```python
@dataclass
class DimSpec:            # 一个受控尺寸
    name: str
    value: float
    tol: float            # 公差带（mm），默认按 GB/T 1804 的 m 级取
    grade: str            # 'vertex' | 'edge' | 'face'
    how: str              # 测量方式：'bbox_x' | 'hole_dia' | 'groove_pitch' | 'axis_dist'

def verify_tolerance(polys, table):
    rep = Report()
    for spec in table.dim_specs:
        got = MEASURE[spec.how](polys)                 # 从几何真的量
        dev = abs(got - spec.value)
        rep.add(spec.name, want=spec.value, got=got, dev=dev, ok=dev <= spec.tol)
    # 几何有效性（face 级）
    rep.add('watertight', ok=is_closed(polys))
    rep.add('min_wall', ok=min_wall_thickness(polys) >= table.min_wall)
    rep.add('self_intersect', ok=not has_self_intersection(polys))
    return rep
```

**要落地的测量算子**（`MEASURE`）：
| 算子 | 用途 | 实现要点 |
|---|---|---|
`bbox_axis` | 总长/总宽/总高 | 包围盒，含 O(n) 顶点扫描
`circle_dia` | 孔径/外径 | 在指定 Z 高度取截面，拟合圆（最小二乘）
`groove_pitch` | 带轮槽间距 | 沿轴向扫描半径极小值位置，取相邻间距
`tooth_count` | 齿数 | 在节圆截面统计半径跳变次数
`coaxial` | 同轴度 | 两回转体轴线的偏差（按顶点集合的质心投影）
`wall_thickness` | 最小壁厚 | 体素/射线双向距离的近似

**验收**：故意注入 5 类超差（孔径偏 0.2 mm、槽距偏 0.5 mm、壁厚偏 0.3 mm…），
**必须 100% 被拦下**并给出"哪个尺寸、期望多少、实测多少、偏差多少"。

## §0.28 真实几何驱动迭代（本次：从"按型号猜"到"按实测建"）

**用户原话**：「将建模助手进行一次迭代升级，这次是真实的数据，要就是先让 ai 明白
是什么，现实长什么样，而不是让 ai 凭空捏造，这样建模的精确度就会严格按照实际参数
来执行。」

### 0.28.1 先把"真实"修对：两个把 521 件数据全污染了的解析缺陷

在动手做"真实几何驱动"之前，必须先确认手上的实测数据**真的是实测的**。
实测发现此前那版 `kb/real_geometry.json`（521 件）**整体不可用**，原因有两个，
都是解析器的缺陷，不是数据的问题：

| # | 缺陷 | 现象 | 后果 |
|---|---|---|---|
| 1 | 把 CATIA 的**构造直线**上的点也算进包围盒 | CATIA 把 `LINE` 的 `'Line Origine'` 写在**半径恰好 500000 mm** 处（实测吊环 M16 的点 `(496770.711, 8.5e-11, -56759.796)`，模长 = 500000.000） | 吊环量成 `993541×17.7×707079`，**521 件全被污染** |
| 2 | 数值正则 `-?\d+(?:\.\d+)?` **匹配不了 `-0.`** | CATIA 的坐标里有大量 `-0.`／`123.` 形式；实测 `M8x20.stp` 有 36 个顶点，旧正则只认下 2 个 | 大量顶点被静默丢弃，包围盒算成 `8.4×0×0.8` |

修法：包围盒只用 `'Vertex'` 点，并按几何公式补齐圆弧极值
（圆在过 `point`、法向 `axis` 的平面内、半径 r，则它在世界轴 e_i 上的最大偏离
= `r·√(1−(axis·e_i)²)`，这是精确式）；数值 token 改为
`[-+]?(?:\d+\.?\d*|\.\d+)(?:[Ee][-+]?\d+)?`。

修完立刻见效——内六角螺钉的实测外形**逐条对上国家标准**：

| 规格 | 实测 X | 实测 Y | 实测 Z | 依据 |
|---|---|---|---|---|
| M5x16 | 10.00 | 10.00 | 21.00 | X=Y=平垫外径 GB/T 97.1；Z=16+头高 5.0（ISO 4762） |
| M8x20 | 16.00 | 16.00 | 28.00 | Z=20+8.0 |
| M10x30 | 20.00 | 20.00 | 40.00 | Z=30+10.0 |
| M12x120 | 24.00 | 24.00 | 132.00 | Z=120+12.0 |

**55 个螺钉里 54 个三条公式同时成立**（唯一例外 `M12x40` 实测总高 57 ≠ 52，
是源模型自身的偏差，如实记录、不去改公式迁就它）。

### 0.28.5 验收：命中率与"判据对不对"

**这一版最重要的教训是判据本身要经得起查。** 第一版基准只比
`PartDef.bbox(p)` 的**声明值**（"这个零件应该多大"），不是测量值——于是出现

（真的跑一遍 BSP-CSG 再从网格顶点量）之后，当场抓出 3 个假通过：

- 吊环 M16：声明 89.5×63×35，**实际建出来** 89.5×35×35（把最大圆柱当成了环体外径）

## §0.29 CATIA 通道故障修复（现场报障：只出了一个杆和一个头）

**用户报障**：「软件出问题了」+ 截图。把「内六角螺栓 M5x16」发到 CATIA 后，
CATIA 里只有螺杆和螺钉头，日志报 `孔: 缺少对象`、`弹性垫圈 ⌀8.8×1.2 : 缺少对象`、
`MakeSketch(7) Sketches.Add failed: 方法 Update 失败`、`features done: -2/4`。

### 0.29.1 根因：一条**零深凹槽**毒死了整棵 Part

从 CATIA 侧留下的推送日志（`%TEMP%\ai_modeler_push_*.log`）还原出因果链：
第 3 条特征「内六角孔」是一次**六边形轮廓的凹槽**，导出成
`poly_cut|…|depth=0`。而 `depth` 为什么会是 0 —— 凸台转切除时只改了 `kind` 和 `z`：

```python
if is_cut and not e['kind'].endswith('_cut'):
    e['kind'] = e['kind'].replace('_pad', '_cut')
    e['z'] = e['z'] + e['h']        # 只挪了草图位置
    # 缺一句 e['depth'] = e['h']
```

而切除类导出读的是 `depth`（`hv = depth if kind.endswith('_cut') else h`）。

**关键认知**：零深凹槽在 CATIA 里**不是"没效果"，而是让整棵 Part 进入 update
报错状态**，此后每一次 `Sketches.Add` 全部失败（报「缺少对象」）——
用户看到的"只剩杆和头"就是这个连锁反应。

### 0.29.2 一连串同源缺陷（用新写的全量检查抓出来的）

修完主因后，我写了 `tools/check_catia_export_real.py` 把**全部 523 个真实型号**
过了一遍导出检查，又抓出三个同类问题：

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | `poly_cut` 缺 `depth`（本次故障） | 整棵 Part 报废 | 补 `depth = h`；并在 Python 端与宏端**各拦一道零深特征** |
| 2 | 六角孔按 `s/2` 当外接半径、且放在头中部 | 对边只有 0.866s（M5 做成 3.46 而非 4）；头顶留 1 mm 盖子 = 没有六角孔 | 外接半径取 `s/√3`（使对边 = s）；剖面底面摆到 `hk − 深度` |
| 3 | `_clamp_cuts` 取 `min(所有直径)` 当外轮廓 | 对"螺钉+两个垫圈"多体件就是螺杆 ⌀5 → 两个垫圈孔都被钳成 ⌀4.8，再被去重合并掉一个 | 改取 `max`（要拦的"内径>外径"依旧拦得住） |
| 4 | 吊环环体在 **Y 轴** | 导出通道只认 Z 轴 → 环体被**静默跳过**，CATIA 里只剩螺杆 | 导出器支持 X/Y/Z 三轴（记录加第 11 段轴字母；宏按轴选 PlaneYZ/PlaneZX/PlaneXY） |

另有**一处既有缺陷**（不在本次改动范围，如实列出、本轮未修）：
`多槽带轮` 的 3 条 V 形槽原本也被导成 `depth=0` 的 `poly_cut`；更本质的是
**V 槽是回转切除**，而本通道只有"草图 + 凸台/凹槽"两种线性操作，原理上做不出
环形槽。现在改成**只出准确的光轮盘体**，并把标准槽参数（标准号/bd/hf/ha/e/槽角）
写进提示让用户用「旋转槽」补 —— **不再伪造做不出效果的假特征**。

## §0.30 细节复现：把"孔的位置"用起来（用户："其他零件都只是大体形状"）

**用户报障**：「现在就螺丝的复现度有 95%，其他零件的复现都只是一个大体形状，
零件细节都没有……相似度不在 95% 以上的就进行修复，要求全部模型都能够用 AI 提示词
建模出来的与实际建模的相似度有 95% 以上。」

### 0.30.1 根因：上一轮只用了几何的"三件套"，位置全丢了

上一轮建每个零件只用了：**包围盒**（外形）+ 圆柱面**直径**指纹 + 实体/面计数。
**孔的位置信息完全没被使用**，所以孔只能"按预算平均摆在长边上" ——
外形对得上、细节全不对。用户看到的正是这个。

### 0.30.2 补上的能力：从 STEP 提取"带位置的真实特征"

新增 `tools/extract_step_features.py`：把每个圆柱面解析成

> 直径 `d` + 轴线（X/Y/Z）+ 轴线在垂直平面上的位置 `(u, v)` + 轴向范围 `z0~z1`

`z0~z1` 由同一轴线上的端面圆推出，所以能区分**通孔 / 盲孔 / 沉孔**；
落在包络外的（CATIA 构造几何）自动剔除并计数。成果落 `kb/real_features.json`
（518 个零件，12.6 MB），再由 `ai_modeler/realholes.py` 整理成"可建模孔清单"。

实测例子（分气块 KMS-M15-G14-H06）：⌀15×2 侧向气路（深 101）+ ⌀11×8 沉孔（深 9）
+ ⌀6.6×2 通孔 —— 12 个孔全部按实测位置/深度/轴向建。

### 0.30.3 一套新的、可复核的"相似度"

|---|---|---|

| 圆柱面数量 S_cnt | 0.20 | min/max 比值 |

## 0.32 A′ 计划：把布尔做成"局部"的（这一步同时修掉了两个一直没被发现的错）

### 0.32.1 为什么要做

`csg_subtract` 是 csg.js 那套实现：**每切一刀**都要
① 拿全部面片重建一次 BSP 树、② 整棵树取反两次、③ 把每张面片对着刀具的
每个平面切一遍。后果有两个：慢（545 个孔的型材几十秒；96 个孔 5 分钟），
以及**面片越切越碎、体积误差随孔数累积**（192 个孔时 2%）。

A′ 的做法（`kernel.solid_cut`）：

* 实体用一棵 **BSP 累加器**维护（`solid_begin`），切除**就地**做，不重建树；
* 每个结点带**子树包围盒**（只增不减的保守盒），与刀具包围盒不相交的子树
  **整棵跳过** —— 一次切除只碰刀具附近那几片；
* 共面情形显式处理，不再靠"整树取反"来对调内外语义。

### 0.32.2 拿解析体积一验，发现旧实现自己就是错的

我一开始是拿"新实现 vs 旧实现"做等价性验收的，结果**两边都对不上解析值**。
把解析值当真值一量，暴露出旧实现的一个系统性错误：

| 情形 | 解析体积 | 旧实现 | 偏差 |
|---|---|---|---|
| 方块 60×60×20 + ⌀20 通孔（**刀两端外伸**） | 65788.3 | 62682.5 | **多切 4.72%** |
| 同上，但刀端面与零件端面**齐平** | 65788.3 | 65788.3 | 0 |
| 圆管 ⌀30/⌀25×40（内孔刀两端外伸） | 8541.0 | 452.9 | **多切 94.7%** |
| 三向交叉孔 ⌀8（EGT006 的拓扑） | 210439 | 207908 | 多切 1.19% |

规律很清楚：**刀具体端面与零件端面齐平时是对的，一旦外伸就多切**。
而"外伸"正是我们最常见的通孔做法（`_build_holes` 让刀两头各长出 10 mm）——
也就是说**旧版本所有通孔都是多切的**，只是外壳判据（包围盒）看不出来。

A′ 之后（`tools/check_bsp_local.py`，10/10 通过）：

| 用例 | 旧偏差 | 新偏差 | 旧耗时 | 新耗时 |
|---|---|---|---|---|
| 4 / 16 / 48 个通孔 | 0.06% ~ 0.08% | **0.009% ~ 0.07%** | 0.03/1.5/62 s | **0.01/0.6/27 s** |
| ⌀20 通孔·刀外伸 | 4.72% | **0.017%** | 0.00 s | 0.00 s |
| 圆管（内孔刀外伸） | 98.3% | **0.5%（解析值一致）** | 0.01 s | 0.01 s |
| 三向交叉孔（EGT006） | 1.19% | **0.009%** | 0.07 s | 0.04 s |

判据不是"跟旧实现比"，而是：**体积 vs 独立估计值**（蒙特卡洛按多边形化几何，
与网格无关）+ **封闭性**（随机取点，解析判定 vs 网格射线奇偶必须一致）。

### 0.32.3 一个差点写错的剪枝

我顺手也给旧的 `node_clip_to` 加了同样的包围盒剪枝，selftest 立刻报错：
方块 + 通孔从 118433.7 变成 117128.4（多切 1300 mm³）。
原因是 `csg_subtract` 会**先给 A 取反**再调用它，"与包围盒不相交"在那一步
意味着"在实体之外"，而这一步要丢的恰恰是"之外"的部分 —— **跳过的方向正好相反**。
结论：剪枝必须**显式知道裁剪方向**（`solid_cut` 里用 `keep=` 表达），
所以旧函数已恢复原样，并在注释里写明了这条。

### 0.32.4 同一轮修掉的另外两个错（都是"验收看不见"的那一类）

**① 孔位整体错位（坐标系不一致）。**
孔位坐标是从实测 STEP 直接搬来的（实测坐标系），可实体原先一律按
"排序后的外形、以原点为中心"摆。实测垫片 `KMS-M09-H03-20-20`：
真实孔在 Y=8、零件中心 Y=25（距中心 −17），模型把实体居中后同一个 Y=8
变成"距中心 +8"——**错 25 mm**。而旧判据比的是"原始坐标"，一点看不出来。
修法：`realparts._measured_frame(p)` 给出实测外形与包围盒中心，
所有用实测数据建的零件（型材 / 支座 / 销座 / 垫片 / 分气块 / 外购件 / 卡箍…）
实体一律摆在**实测坐标系**里。同时把判据也改了：孔位一律换算成
"相对自身包围盒中心"再比 —— 刚体平移不影响分数，但"零件被换了方向、
孔落在实体外面"会立刻扣分。这一改，很多族从"看起来 100%"掉到了真值
（垫片/销座/支座 50% → 修好后回到 100%；EGT006 ⌀30 圆棒 21% → **98%**）。

**② CATIA 导出的孔位沿对角线镜像。**
提取器给的 (u,v) 是**下标升序**的另外两轴（Y 向孔 → u=X, v=Z），
而 CATIA 草图平面按 PlaneZX 排（Y 向孔 → (Z, X)），两者对 Y 向孔**正好互换**。
特征表照样"合法"（523/523 全绿），但孔会镜像。修法：导出时显式换一次，
并新增 `tools/check_catia_hole_positions.py` —— 把导出的孔位**反算回零件坐标系**
与实测圆柱逐个比对，**267/267 型号、74601 个孔位全对**（±0.01 mm）。

**③ 重复切除合并规则吃掉了真孔。**
`_dedupe_cuts` 只比 (cx, cy, r)，不看平面 —— 型材 13 个实测孔被合并掉 3 个
Z 向孔（导出只剩 10 个）。修法：平面必须相同，且距离阈值收到 0.5r。
已加进 selftest（"CATIA: 重复切除合并规则"）。

### 0.32.5 第二层剪枝：把"走树"也剪掉（48 孔 72s → 6.8s）

第一版 `solid_cut` 只按**结点子树包围盒**剪枝，实测圆管 ⌀30×1000 上 48 个孔
仍要 72 s（每刀 1.5 s，cProfile 显示每刀 **16 万次 `split_polygon`**）。原因：

* 结点的包围盒是"只增不减"的保守盒，跑过几十刀后**高层结点的盒子包住了整个零件**
  → 只按结点判，几乎所有结点都被认为"与刀相交"；
* 于是几千张**离刀很远的长面**也被塞进 `node_clip_polygons`：刀具的侧面平面是
  **无限大**的，10 mm 外的长面照样跨过它们，被切成一堆没用的碎片。

修法（两条，都在 `solid_cut` 里）：

1. 走树时**子结点也按包围盒剪**（这里的动作方向是明确的 —— "丢掉落在刀具内部的
   面片"，所以"子树与刀具盒子不相交 ⇒ 不用切"成立）；
2. 进 `node_clip_polygons` 之前再按**每张面片自己的包围盒**过滤一次。

实测：⌀30×1000 的 48 孔 **72 s → 6.8 s**、102 孔 11.5 s、支座(铝) 94 刀 14.1 s → 8.5 s，
10/10 等价性验收与 35/35 自检都不变。

### 0.33.2 图像相似度：**真实照片这一路不能用**（有实测证据，不遮）

我按"轮廓 chamfer 匹配"做了完整实现（`tools/compare_ai_vs_real_images.py`，
配准、对称 chamfer、P/R/F1 全都有），并用**真配对 / 交叉配对**做了标定：

| 标定 | 平均"命中率" P |
|---|---|
| 真配对（M5x8 的渲染图 vs M5x8 的真实照片） | **85.3%** |
| 交叉配对（M5x8 的渲染图 vs 别的零件的真实照片） | **84.1%** |

**只差 1.2 个百分点** —— 也就是说：在现有截图上，任何轮廓都有 ~85% 的点能落在
"某条边缘"上。这种指标没有区分能力，拿来当"相似度 ≥95%"的验收就是自欺欺人。

根因（都验证过）：
* 真实照片是 **CATIA 整窗截图**：左侧规格树、顶部工具栏、深红**渐变**背景；
* 背景渐变带抖动，梯度图里是成千上万个小噪点（实测 Canny 出 1171~4757 个连通域）；
* 零件的边缘反而很弱（灰度对比只有几十），模糊后梯度 ~20，低于常用 Canny 阈值；
* 试过的补救（降阈值 / 形态学开运算 / CLAHE 增强 / 最大连通域 / 区域生长 / 洪水填充）
  都会在"噪声被清掉"和"零件轮廓被一起清掉"之间二选一。

**结论与出路**：要让"图 vs 图"可比，**真实侧必须白底重拍** ——
`tools/capture_real_images.py` 已加 `--white-bg`（隐藏规格树/工具栏 + 3D 背景纯白），
重拍后零件是深色实心块、背景纯白，掩码可直接阈值分割，图像相似度才真正可比。

### 0.33.3 不依赖照片、因此可信的两个图像口径

| 口径 | 结果 | 说明 |

| AI 渲染图 vs 实测几何渲染图（同渲染器同视角，掩码精确） | 螺栓族 **58.6%** | 同上原因：参考几何是"包围盒 + 圆柱孔"，对螺栓就是"一个方盒"，与真实螺栓形状本来就不同 |

## 0.36 外轮廓复刻（OpenCASCADE + 实测 B-Rep）：把图像相似度从 62% 抬上去

### 0.36.1 问题定位（数据说话，不是猜）

图像相似度第一次算准之后：**平均 62.1% / 0/313 ≥95%**。逐件看并排图，根因非常明确：

| 零件 | AI 侧轮廓 | 真实侧轮廓 | 差在哪 |
|---|---|---|---|
| `KMS-M05-010-100-D`（支座） | 一个**方块** | **L 形支架** | 型腔/台阶全丢 |
| `EGT001 SW80x1018`（型材） | 斜长条（角度对） | 斜长条（更长更薄） | 端部细节/厚度 |

原因：非标件走的是 `_box_features(实测包络)` = **包围盒 + 孔**。
几何判据只量孔径/孔位/包络，**量不到外轮廓**，所以长期显示 91.9% 的高分。

### 0.36.2 方案：用实测 B-Rep 当几何（而不是靠"特征识别"硬猜）

**思路**：与其把 B-Rep 反推成参数化特征（研究课题），不如
**用 OpenCASCADE 读实测 STEP/STL → 三角化 → 直接当模型几何**。
对外轮廓的还原是**严格精确**的，而且下游（渲染/度量/比对/导出）一行都不用改。

新增：
* `tools/build_real_brep.py`：STEP/STL → `kb/real_brep/<型号>.npz`（float32 顶点 + int32 三角面，
  压缩存储；含体积/包围盒/面数索引 `kb/real_brep_index.json`），**支持 STL**（STL 无需互操作许可）；
* `ai_modeler/realsolid.py`：`available/polys/cylinders/volume` —— 加载器 + 供判据使用；
* `docmodel` 新增特征 **`real_solid`**（一条特征 = 整个真实零件）；
* `realparts.build_real_generic` 改为**优先实测 B-Rep**，取不到才退回原来的
  "包络长方体 + 实测孔位"（`AI_MODELER_REALSOLID=0` 可关掉做 A/B）。

**边界（必须写清楚）**：
* 标准件（螺栓/齿轮…）**继续走参数化构建器** —— 那才叫"用提示词建模"；
  只有"用实测数据的族"才优先实测 B-Rep，因为对"复刻真实零件"这个目标它严格更接近；
* 这是**复刻**（几何来自实测），不是"从参数生成"；特征名里写明
  "实测 B-Rep 复刻（型腔/筋/台阶来自 STEP 实测）"，界面上看得见；
* CATIA 通道：自由曲面无法用"凸台+圆孔"的特征表表达 → 这类零件改为**导出实测 STEP**，
  导出时会给出明确提示（不假装能建）。

### 0.37.2 问题二（自查发现）：四个"一键脚本"里三个**根本跑不起来**

顺手用**真正的 Windows PowerShell 5.1 解析器**逐个解析包里的脚本，结果：

```
[OK]           01_安装依赖.ps1
[PARSE-FAIL 2] 02_跑全流程.ps1     ← The string is missing the terminator: "  (line 38)
[PARSE-FAIL 4] 03_重建大数据.ps1    ← Missing closing '}' in statement block  (line 18)
```

根因：这些 `.ps1` 是 **UTF-8 无 BOM**。Windows PowerShell 5.1（就是双击 /

紧接着**语法解析失败**——队友双击只会看到窗口一闪而过，没有任何人能看懂的错误。
同理 `.bat` / `.vbs` 必须是 GBK(ANSI)，否则 cmd 与 WSH 读中文路径会读坏。

修法：新增 `tools/fix_script_encoding.py`（幂等）——
`.ps1` 加 UTF-8 BOM、`.bat`/`.vbs` 转 GBK、UTF-16 与纯 ASCII 不动。
修完再解析：**5 个脚本全部 `[OK]`**。

这条已经写成判据进 `check_share_pack.py`（"脚本编码不对 = 0"），不会再悄悄退化。

## 0.37.9 "队友更新了代码我怎么用"：拉取 + 镜像 + 门禁 + 回滚，一条命令

用户问的是使用问题，但背后藏着一个**结构性问题**，必须先把事实摆清楚（都实测过）：

| 事实 | 数字 |
|---|---|
| 仓库里只有代码 | 602 个文件，仓库体积 3.2 MB |
| 大数据故意不进仓库 | `kb/real_brep` 116 MB、`kb/real_brep_coarse` 115 MB、`_wheels` 513 MB、照片/比对图约 42 MB、`零件参数`（客户资料） |
| 大数据在**工作目录** | `C:\Users\25643\Desktop\ai自动建模插件` |
| 工作目录**不是 git 仓库** | 无 `.git` / `.gitignore` / `.gitattributes` |

所以"用队友的更新"= ① 在协作包（= git 工作副本，结构与仓库完全一致）里 pull；
② 把这次改动的文件**按原目录布局**镜像到工作目录。
只做①的话，队友的新代码躺在一个没有数据的目录里，跑不了真实零件那条路。

### 做法：`tools/git_sync.py`

四步，每步都可核对：

1. `git fetch`（令牌走内存，不需要输密码）；
2. `git merge --ff-only origin/main` —— **不允许自动生成合并提交**，有本地改动会明确失败；
3. 按 `git diff 旧..新` 的清单镜像到工作目录（**只碰队友改过的文件**）；
4. 在**工作目录**里跑 `python -m ai_modeler --selftest` 当门禁。

镜像环节的三个设计考虑（都是踩过才知道要写的）：

* **保持用户原来的布局**：仓库里文档归档在 `docs/历史报告/`、脚本在 `启动脚本/`，
  而用户工作目录里它们在根目录 → 识别"重新归档"，仍写回根目录，不凭空多建目录；
* **队友删掉的 文件要先验证**：拿 git 哈希比对本地那份有没有被改过，改过就打印
  `[保留(你本地改过)]` 不删；
* **覆盖前先备份**到 `_mirror_backup\<时间戳>\`（工作目录不是 git 仓库，没有 git 兜底）；
* **内容比较用 git 自己的哈希**（会按 `.gitattributes` 归一化换行）——
  一开始用 md5 比，结果"只是 CRLF/LF 不同"也被判成改动，白白重写并多出一份备份（已修）。

### 实测（不是"应该能行"）

| 测什么 | 怎么测 | 结果 |
|---|---|---|
| 镜像 + 门禁 | 协作包建临时分支 `_sync_probe`，加文件提交，工作区跑 pull | 检出 1 个新提交 → 文件落到正确位置 → 自检 **35/35** ✔ |
| 真实网络路径 | 协作包 `reset --hard HEAD~1` 后跑 pull | fetch（内存令牌）→ 快进 `6321cc6 → ca1d028` → 镜像 → **35/35** ✔ |
| 内容相同（仅换行差异） | 上一步镜像的正是 `.md` | `已一致 1 个`，不重写、无多余备份 ✔ |
| 回滚 | `rollback` | 协作包 HEAD 退回，工作区还原逻辑走通 ✔ |
| 清理 | 删临时分支/探针文件/备份目录 | HEAD = 远端 main，`git status` 干净 ✔ |

### 同时补上的东西

* `scripts/07_拉取队友更新.ps1`（双击版，带 BOM）；
* `docs/guides/用队友的更新_操作手册.md` + 桌面 Word：为什么不能只 `git pull`、
  四步做了什么、门禁不过怎么回滚、**哪些大数据不会跟着走以及怎么重建**、
  常见问题（冲突 / 队友误推大数据 / 我自己的改动怎么推上去）；
* README 的"协作方式"补了两种情况：**在仓库目录里工作 → `git pull` 就够**；
  **"仓库 + 带大数据的工作目录"→ 用 `git_sync.py`**。

### 一条诚实的限制（写进文档了）

工作目录不是 git 仓库，所以**无法自动判断"某个文件你是不是也在改"**。
同一个文件双方都改，脚本只能按"队友的版本优先 + 本地先备份"处理。
要真正解决，得把工作目录也变成 git 工作副本 —— 但那需要先搬几个目录的位置
（顶层文档/启动脚本归档进子目录），会改变用户熟悉的使用习惯，所以**没有擅自做**，
等用户哪天要"常态化双向协作"再说。

## 0.37.11 用户双击后"纯黑窗口"：三个原因叠在一起，一个比一个隐蔽

用户截图：Windows Terminal 标题是 `Sync Assistant`，**窗口全黑，一个字都没有**。

### 排查（先排除掉最容易误判的那个）

第一个怀疑是"`where python` 找到了微软商店的 python 别名桩"（那个桩跑起来什么都不干，正好是黑屏）。
**实测否掉了**：把环境变量清空、只用注册表里的用户/系统 PATH 模拟双击，
`where python` 找到的是真 Python 3.14，`python -c "print(123)"` 输出 123、退出码 0。
（这个桩确实存在：`%LOCALAPPDATA%\Microsoft\WindowsApps\python.exe`，所以启动器还是加了校验。）

### 真正的原因：三个问题叠在一起

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | 菜单**第一行输出**要等 `status()` 跑完才打印，而 `status()` 里有一次**没有超时**的 `git fetch` | 网络慢/被挡时，窗口一直是纯黑的（连"我在跑"都看不出来） | 先打印横幅（`flush=True`）；fetch 加 **20 秒超时**；超时/失败就**按本地状态继续**，并在状态区标 `[离线]` |
| 2 | `status()` 里 `scan_out()` 对仓库里 **609 个文件每个都起一次 `git hash-object`**，外加一次 `git rev-parse`（约 **1200 次进程启动**，Windows 每次 ~30ms） | **刷新一次状态要 30 秒** —— 用户等到的就是"半天什么都不出来" | 改成**纯 Python 读文件比较**：文本按 `\r\n`→`\n` 归一化后比字节，二进制逐字节比。**30 秒 → 0.26 秒** |
| 3 | stdout 非交互时是**块缓冲**，几百字节的输出会一直躺在缓冲区里 | 即使有 print 也看不到（截图里就是这种情况） | `console_io.setup()` 里 `reconfigure(line_buffering=True, write_through=True)` + 自建 `Tee` 每次 write 都 flush |

### 顺带做的两件"以后好排查"的事

* **写日志**：菜单把全过程写到工作目录的 `_sync_assistant.log`（控制台看不到时，日志能看到卡在哪一行）；
* **启动器先说人话**：`同步助手.bat` 一进来就 `echo [Sync Assistant] starting...`，
  再回显它选中的 python 路径，并**用 `python -c "import sys"` 验一下真能跑**（躲开商店别名桩）。

### 教训

**"用户看到的是黑的"这件事，本身就是缺陷 —— 程序有责任在任何时刻都让人看到"我在跑"。**
这次三个原因里，只有第 2 个是性能问题，第 1、3 个都是**可见性问题**：
我写交互程序时默认"输出会立刻出现在屏幕上"，而实际上
（a）我把第一行放在了耗时操作之后，（b）非交互/管道场景下 Python 会缓冲。
以后凡是有联网/重活的交互程序，第一条规矩就是：**先说话，再干活；每条都 flush。**
